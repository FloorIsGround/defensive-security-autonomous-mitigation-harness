# Adaptive investigator design and implementation priorities

The [development charter](DSAMH_Adaptive_Autonomous_Investigator_Development_Direction.md) governs product direction after P12–13. The inventory in section A describes the starting point at `f6a611c`. The integration record below identifies what can now be demonstrated on `feat/adaptive-investigator`. The [v0.2 design](../adaptive_defensive_monitoring_harness_design_v0.2.md) and P10/P12 contracts describe earlier milestones.

**The first demonstration should start with a quiet host.** Given enrollment, authorized scope and a resource budget, the investigator should discover what the host appears to do, cite the evidence, identify what it cannot see, and choose what to monitor next. An administrator should be able to inspect the result without having supplied a service inventory or opened an incident. Optimize for correct conclusions, useful monitoring and operator time saved. Measure model cost and latency alongside those outcomes.

## A. What we can build on

| Area | What works on this branch | Where the design must change |
|---|---|---|
| Run lifecycle | Both run-start requests take an incident ID. Delegated runs have scoped credentials, expiry, cancellation and progress events. Trigger leases support reactive workers. | Give a run a host and purpose independent of an incident. Separate a durable investigation and its outstanding questions from an individual model attempt and credential. |
| Discovery | Six typed collectors cover listening sockets, outbound connections, packages, unit state, file metadata and journal events. Host registration reports a profile summary. Capability listing filters by central floor and caller scope. | Show what this host can currently supply, including disabled, unsupported, partial and stale sources. Unit state for a known unit and per-socket attribution provide only a partial service inventory. Record missing capabilities such as service enumeration for trusted extension review. |
| Evidence | Scoped observation queries, incident context and findings already link conclusions to samples. Stored observations reference a specific watch version. | Collect an immediate sample independently of a watch. Keep its source, scope, time, completeness and evidence identity queryable alongside scheduled samples. |
| Monitoring | An accepted ephemeral proposal can install a bounded follow-up watch. Admin can apply a baseline watch. Control signs desired state and edge checks it locally. | Add delegated durable watch management, expected signal, owner, hypothesis, evidence, review date and explicit change impact. Enforce minimum coverage through replacement and expiry. |
| Baselines and rules | Control tracks accepted, previous and current state. Admin promotes baseline revisions. Investigators can read summaries and propose expectation rules. Admin can backtest, decide and revoke rules. | Introduce provisional expectations, candidate comparison and policy-evaluated low-risk promotion. Make scoped backtest impact visible before any delegated rule activation. |
| Host knowledge | Admin-owned local profiles constrain collection. A registered summary, incident findings and the run timeline provide context. | Store versioned investigator assessments of roles, dependencies, maintenance patterns, coverage and unresolved hypotheses. Keep inferred facts distinct from authenticated intent when evaluating trust. |
| Response | A run can propose a typed action with evidence, expected effect and rollback plan. Control and the executor enforce their respective gates. Control stores receipts. | Connect receipts to verification runs with measurable postconditions. Preserve unknown outcomes across retries and support recovery assessment. |

## B. Discover one unfamiliar host

1. **Start from enrollment.** Control queues a host-scoped discovery objective once per enrollment generation. An operator can also request discovery. A worker leases the objective and gets a short-lived child credential restricted to that host, purpose, permitted collectors and evidence scope. Keep existing incident RPCs and their authorization checks. Migrate existing runs as reactive, deriving their host from the incident. A discovery run must never satisfy an operation that requires an open incident merely because both concern the same host.
2. **Choose evidence.** Extend the existing capability listing with versioned inputs, output semantics, cost bounds, sensitivity, host support, registration freshness and limits on attribution. Intersect the advertised capability with caller scope and current policy at admission. A missing profile from an older agent means support is unknown. Start with bounded socket and package snapshots, then inspect a known unit if attribution and scope allow. Add a capability through reviewed, tested and versioned agent releases when a recurring question needs a new source.
3. **Collect once.** Use an asynchronous typed request keyed by run and idempotency key. Control records the normalized parameters, host, deadline, limits and policy decision before dispatch. The enrolled agent receives a signed, expiring request over its existing connection, checks its local floor and invokes the registered collector. Negotiate support before dispatch to older agents. Expose pending, completed, denied, expired, failed and cancelled outcomes, with explicit partial or truncated coverage on returned evidence. A disconnected agent leaves a request pending until its deadline.
4. **Keep evidence attributable.** Store a one-shot result keyed to the request, with a stable evidence reference, collection and receipt times, source version, digest and collection status. Extend evidence lookup to accept scheduled or one-shot references and check their host and collector scope at read and citation time. Preserve the current observation-to-watch foreign key. Repeating a request with identical parameters returns the same job, a changed payload under the same key is rejected, and a repeated delivery cannot commit two results. Late results cannot complete a cancelled run or update a baseline.
5. **Write a revisable assessment.** Persist a host assessment revision with inferred role, supporting and conflicting evidence, dependencies, visibility gaps, unanswered questions and proposed watches. Only authenticated configuration can alter collection policy. Present typed operations through Investigation RPC and MCP, and expose the same evidence and denials to the Python worker. Apply a separate export decision before constructing an external model request, including resumed context and tool results.

**Acceptance.** Enroll a disposable service host with bootstrap collection and no declared role. From the worker entry point, obtain fresh evidence, identify its fixture role with supporting references and explain one deliberately unavailable source. Retrieve the assessment after restarting control. Repeat using MCP with the same grants. Verify an out-of-scope request is refused, an older agent reports unavailable support, and duplicate submission and disconnect produce one terminal outcome. The exercise creates no incident, persistent watch, trusted baseline or action as a side effect of sampling.

## C. Let the investigator establish useful monitoring

Turn the discovery assessment into an ongoing strategy. For example, if a host repeatedly presents a packaged service and a listening endpoint, the investigator can install a permitted durable watch for that service, retain the evidence that motivated it and schedule a review. A second unexplained listener remains an open question. Its continued presence supplies observations but confers no trust.

| Decision | Who may decide under the proposed adaptive profile | Evidence and invariant |
|---|---|---|
| Add, test, update or renew bounded coverage | Investigator within a per-host or group monitoring grant | Control checks the effective old and new spec, scope, cadence, retention and aggregate cost. Record intent, expected signal and decision separately. |
| Reduce coverage, retire a watch or add suppression | Separate reduction grant or operator decision | Evaluate the net effect, including replacement, expiry and loss of sensitivity. Protect bootstrap controls and enforce coverage floors across concurrent changes. |
| Record a provisional expectation | Investigator within host scope | Link observations and uncertainties. Provisional state can guide additional collection. Suppression and action gates consume only their explicitly authorized inputs. |
| Promote a trusted baseline or activate a narrow rule | Operator by default, or explicit delegation for an eligible class | Require independent corroboration such as authenticated service intent, sufficient observations, no conflicting open finding and, for rules, a scoped backtest. Deny high-impact or ambiguous changes pending stronger review. |
| Change a trust decision | Attributable authorized principal | Compare against the expected predecessor, record policy version, evidence, rationale and outcome. Preserve earlier revisions and support rollback to a prior expectation with an audit record. |

Retain the observer profile for proposal-only administration and the separately enabled response profile for bounded reversible actions. Grant reads, provider export, additive monitoring, trusted changes and response independently. Restrict every operation by host, capability and risk. Only operator administration can expand those grants.

**Acceptance.** On a fresh fixture, install a useful persistent watch without per-watch approval. Inject an authenticated maintenance change and an unrelated unexplained change. Demonstrate a provisional expectation, an eligible promotion, a denied promotion, and rollback. Replay the observations to show the unexplained change still alerts. A concurrent renewal and retirement must preserve minimum coverage and audit the winning revision.

## D. Resume the investigation across time and providers

See the [ChatGPT investigator and analysis sandbox proposal](chatgpt-investigator-and-analysis-sandbox.md) for account connection, case checkpoints, evidence analysis and engine comparison.
Use the same durable objectives for scheduled assessments, profile changes, timed follow-ups and supervisory review. Persist the next question, due time, evidence references, last completed step and outstanding jobs. A lease fences the active attempt. After cancellation, expiry, provider failure or budget exhaustion, record the reason and remaining work. An authorized successor receives a fresh, possibly narrower token and rechecks access before loading context. Deduplicate scheduled work and bound concurrency so discovery cannot starve reactive investigations.

Give each purpose its own model route, reasoning effort and tool, time and token budget. Reserve capacity before a call, bound output when the backend supports it, and record actual usage and any overrun. Surface which limits a provider can enforce. A deep assessment may spend more than routine triage when evidence warrants it.

**Acceptance.** Start a timed follow-up on a quiet host, interrupt it after an evidence request, then resume with a different worker from persisted state. Verify the unanswered question and citations survive, no request is duplicated, and deterministic monitoring continues. Test partial telemetry, provider outage, budget exhaustion and revocation during interruption.

## E. Verify response and measure effectiveness

Attach a verification objective to each authorized response receipt. Capture preconditions and expected postconditions before dispatch. Obtain a fresh scoped observation afterward and record verified, contradicted or indeterminate outcome with supporting evidence and any adverse effect. An uncertain execution outcome requires reconciliation before retry. Recovery uses the same applicable action authority. Exercise this flow in a disposable fixture.

Compare **static monitoring**, the **current incident-triggered worker**, and the **adaptive investigator**. Freeze ground truth, held-out variations, scoring rubrics and pass thresholds before exposing fixtures to a model. Give arms identical initial telemetry and comparable budgets. In separate runs vary sensor access and reasoning budget independently. Record model/version, settings, fixture revision, grants, costs and operator interventions so another reviewer can reproduce the comparison.

| Question | Measure and release evidence |
|---|---|
| Did it understand the host and choose worthwhile watches? | Score cited role and dependency claims against hidden inventory, coverage of relevant changes, unsupported conclusions and gaps correctly identified. |
| Did it distinguish maintenance from suspicious drift? | Report precision, recall, false alerts per host-day, erroneous trusted promotions and whether unexplained changes stayed visible. |
| Did autonomy help the operator? | Compare manual decisions, time to detection and verified conclusion, tokens, cost and collection overhead per host. Include incomplete runs. |
| Did it recover and respect scope? | Replay the P13 evidence-gap and budget cases. Exercise stale telemetry, restart, held-out host roles, authorized cross-host correlation, scope loss and unknown action outcome. Require zero unauthorized exports, mutations and trusted promotions. |

Retain the [scripted benchmark](../../reasoner/defsec_reasoner/benchmark.py) as regression coverage. Begin collecting matched static and reactive results during milestone B. Set quantitative effectiveness thresholds against those baselines before running the held-out adaptive arm. Publish failures and uncertainty alongside successes. The next implementation decision is whether discovery yields a defensible, actionable host assessment under realistic visibility limits. That evidence determines which collector or query capability to extend first.

The [November investigator pilot](../evaluation/investigator-pilot-2026-11-25.md) supplies an initial token and evidence baseline for reactive work. Measure the fraction of runs that cite a new observation after requesting it, and carry pending observations into a follow-up objective when an attempt ends.
